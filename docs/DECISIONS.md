# Decision Log

Short records of architectural decisions. Newest at the bottom. Status: Accepted / Superseded / Proposed.

---

## D-001: Git with Git LFS from day one (Accepted, 2026-11-13)
Unity-specific `.gitignore` (excludes `Library`, `Temp`, `Obj`, `Logs`, `Build(s)`, `UserSettings`, generated `.csproj`/`.sln(x)`).
`.gitattributes` routes binary art/audio/font formats to LFS and keeps Unity YAML as LF text.
**Consequence:** a remote must support LFS (GitHub does, with storage quotas).

## D-002: Project root folder `Assets/_WoodcraftSimulator` (Accepted, 2026-11-13)
As proposed in master prompt §8. The leading underscore keeps our content at the top and separate from
template/third-party assets. Folders are created only when a system needs them.

## D-003: Assembly definitions from the start (Accepted, 2026-11-13)
`WoodcraftSimulator` (runtime) and `WoodcraftSimulator.Editor` (editor-only).
**Why now:** EditMode tests (Phase 3) need an asmdef to reference; introducing it later means moving code.
**Consequence:** every new package used by runtime code must be added to the asmdef `references`.

## D-004: Units: meters in the world, integer millimeters in the domain (Accepted, 2026-11-13)
Unity world space uses meters (physics default). Authoritative timber dimensions, cut positions and
measurements are stored as integer millimeters, converted to meters only for presentation.
**Why:** avoids float drift through repeated cuts and conversions (master prompt §6.4).
**Open question (Phase 3):** whether 1 mm resolution is enough (e.g. kerf 2.5 mm). Alternative: 0.1 mm integer units.
**Update:** resolution changed to 0.1 mm, see D-014.

## D-005: CharacterController for the player (Accepted, 2026-11-13)
Per master prompt §6.1. Kinematic, predictable, cheap; no fighting with rigidbody physics.
**Consequence:** the player doesn't push physics objects by default; carried objects are handled explicitly (Phase 2).

## D-006: Project-wide Input Actions via `InputSystem.actions` (Accepted, 2026-11-13)
The template's `InputSystem_Actions.inputactions` is already registered as the project-wide asset.
Actions are looked up by name (`"Player/Move"`) once in `Awake`.
**Alternative considered:** generated C# wrapper class: stronger typing, but adds a generated file and importer setting.
Revisit when the action set grows.

## D-007: Greybox scenes are generated by editor scripts (Accepted, 2026-11-13)
`WorkshopSceneBuilder` builds the test workshop from code. Reproducible, reviewable in diffs, dimensions documented in code.
**Consequence:** manual edits to `Workshop.unity` are lost when the scene is rebuilt. Once the workshop
becomes hand-authored content (Phase 8), the builder is retired.

## D-008: UI Toolkit for screen-space UI (Accepted, 2026-11-13)
Master prompt §6.15 prefers UI Toolkit and forbids unnecessary mixing of UI systems. HUD (crosshair,
interaction prompt) and menus will use UI Toolkit. uGUI only if a concrete world-space need arises.
A first uGUI crosshair draft was removed before commit for this reason.

## D-009: Interaction via `IInteractable` + per-frame camera raycast (Accepted, 2026-11-13)
One `Physics.Raycast` per frame from the camera (2 m, raised to 2.5 m on 2026-11-13 so floor items are reachable),
component lookup only when the hit collider changes.
Interactables are components implementing `IInteractable` (composition, master prompt §6.2).
The HUD reacts to a C# event instead of polling.
**Alternatives considered:** trigger volumes / overlap spheres (less precise for small targets like screws or
marks); SphereCast (more forgiving aim, revisit if small targets feel hard to hit).
**Update 2026-11-13:** SphereCast aim assist (radius 0.08 m) added as a fallback after the precise ray, at the
owner's request (boards on the lower rack shelf were hard to target). Precise ray still wins.
**Consequence:** interactables need a non-trigger collider on the default raycast layers.
In-game text is English for now; localization is out of scope until the UI grows.

## D-010: Static compile check outside Unity (Accepted, 2026-11-13)
Claude verifies code with `dotnet build` on temporary copies of the Unity-generated `.csproj` files
(new files added, `HintPath`s made absolute), scripted in `tools/static-build.sh`. This catches C# and API errors
against the real Unity DLLs without touching the open Editor. It does **not** replace Unity compilation
(Unity's own compiler, ILPP, asmdef rules) or play testing.

## D-011: Pause = timeScale 0 + disabling listed gameplay components (Accepted, 2026-11-13)
`PauseController` owns the paused state and the cursor. It disables the Behaviours in `disableWhilePaused`
instead of every system checking an `IsPaused` flag, so gameplay components stay unaware of pausing.
`Time.timeScale = 0` additionally freezes physics and anything time-based.
**Consequences:** new gameplay components that must stop while paused are added to the list (scene builder);
code that must run while paused (UI, pause input) must not depend on `Time.deltaTime`.
Focus loss pauses the game (also when clicking another Editor window during Play Mode); toggle `pauseOnFocusLoss`.

## D-012: Settings in PlayerPrefs via `UserPreferences` (Accepted, 2026-11-13)
Small player preferences (mouse sensitivity) use `PlayerPrefs` (Windows registry). Game progress will use
a separate versioned save system (master prompt §6.16). `UserPreferences` holds no state of its own.

## D-013: Public GitHub repo, feature branches + PRs (Accepted, 2026-11-13; branching superseded by D-020)
`origin` = https://github.com/OezalA/WoodcraftSimulator (public, owner's choice). `main` starts at the template
commit; work happens on `feature/...` branches merged via pull requests.

## D-014: `Length` with 0.1 mm integer resolution (Accepted, 2026-11-13, refines D-004)
`Length` stores a `long` count of tenths of a millimeter. 1 mm was too coarse for saw kerf (≈ 1.5–3 mm) and
fractional measurements; 0.1 mm is finer than any tape measure reading and still exact under addition.
Doubles (from UI or Unity) are rounded to the nearest 0.1 mm (midpoint away from zero) when converted in.
**Consequence:** all domain lengths use `Length`; float meters only at the Unity boundary.

## D-015: Pure C# Domain assembly, tests runnable outside Unity (Accepted, 2026-11-13)
`WoodcraftSimulator.Domain` has `noEngineReferences: true`, so the compiler rejects any `UnityEngine` use in
game rules. EditMode tests reference only this assembly + NUnit, which lets them run both in Unity's Test Runner
and with `dotnet test tools/DomainTests` (C# 9 like Unity). This is how Claude executes tests while the Editor is open.
**Consequence:** domain code can't use `Mathf`, `Vector3`, `Debug` etc.; conversions live in the Unity layer.
Avoid C# features Unity lacks (`record`, `init` need `IsExternalInit`).

## D-016: Timber geometry generated from data; dynamic rigidbodies for now (Accepted, 2026-11-13)
`TimberBoard` generates its mesh and collider from `TimberPiece.Dimensions`; transform scale stays 1
(scaled transforms complicate child objects, physics and later cutting). Color per species via
`MaterialPropertyBlock` on one shared material (no material per board). Boards are dynamic rigidbodies with
mass from density × volume. Phase 2b will decide the carried/placed physics states.
**Alternative considered:** a unit cube scaled by the transform (simpler, but scale leaks into everything).

## D-017: Initial species data are approximate placeholders (Accepted, 2026-11-13)
Densities (kg/m³, ~12 % MC): spruce 450, pine 520, oak 710, beech 720, walnut 640, larch 590, Douglas fir 530.
These are rounded typical values from general knowledge, **not verified against a cited source**; each asset's
`dataNotes` says so (master prompt §15.19). Verify before any feature claims real-world accuracy.

## D-018: MSAA 4x on the PC quality level (Accepted, 2026-11-13)
The template's `PC_RPAsset` had MSAA off, so geometry edges were jagged. `m_MSAA` set to 4 (Forward+ supports MSAA).
Moderate GPU cost; revisit with profiling in Phase 13 (alternatives: SMAA/FXAA post-process AA, or MSAA 2x).
Note: softness seen in the Editor was mainly the Game view zoom (`Scale` > 1x), not the render resolution.

## D-019: Object handling = kinematic carry + validated placement (Accepted, 2026-11-13, refines D-016)
- **Resting** objects are kinematic rigidbodies: they stay exactly where they were placed (no settling, sliding or
  stack jitter). Master prompt §6.18 "controlled transitions between physical manipulation and fixed state".
- **Carried** objects have their colliders disabled and are moved by code to a hold point in front of the eyes
  (yaw only, so they stay level). They don't block the player or the placement test, but can visually clip into
  walls while carried: accepted simplification for the prototype.
- **Placement**: ray from the camera (3 m) onto a surface ≤ 30° slope; target pose = surface point + rotated
  half-height; `Physics.CheckBox` (shrunk by 3 mm, 2 mm above the surface) must find no other collider,
  including the player's CharacterController. Translucent preview green/red; LMB places only when valid.
- Rotation: R = 90° yaw, T = 90° around the object's length axis.
- While carrying, `PlayerInteractor.IsBlocked` = true (hands full).
**Known consequence:** removing a board from under another leaves the upper one floating (kinematic). Revisit with
support checks or a "settle" step if it matters for gameplay. No free "drop" yet.

Owner's choice: no feature branches. Day-to-day commits go to `develop`; `main` is fast-forwarded to `develop`
once the owner has confirmed the manual tests of a step. The former feature branches were linear and fully

## D-022: Placement feedback names the blocker (Accepted, 2026-11-13)
`PlayerCarrier` exposes `Status` (NoSurface / Valid / Blocked) and `Blocker`, raising `PlacementStatusChanged`
only on change. The HUD shows "Aim at a free, level surface within reach", "Blocked by <object>" or
"Blocked: too close to you". The overlap test now uses `Physics.OverlapBoxNonAlloc` into a reused buffer
(no allocations) instead of `CheckBox`, to know what blocks.

## D-023: Player casts must explicitly ignore the player's own colliders (Accepted, 2026-11-13)
**Finding (from the placement diagnostic log, D-022):** casts starting at the camera, i.e. inside the player's
CharacterController, *do* report that controller when looking down (`surface='Player' distance≈0.09 m`).
The earlier assumption "casts ignore colliders containing their origin" (D-009 comment) was wrong for this case.
Effects: the player's head was taken as the placement surface (floor placement always "Blocked by Player"), and
floor objects were harder to target for interaction.
**Fix:** `Core.PhysicsQueries.RaycastIgnoring / SphereCastIgnoring` (NonAlloc + skip a given hierarchy, closest
remaining hit). Used by `PlayerInteractor` and `PlayerCarrier`. Overlap tests for placement still include the player.
**Rule:** every new query cast from the player's eyes must use these helpers (or a layer setup that excludes the player).
**Kept:** `PlayerCarrier` logs a refused placement (only on click) with surface, distance, normal and blockers.

## D-024: Small items live on a tool belt; one item in hand (Accepted, 2026-11-13)
Phase 3a, the small-item inventory moved from Phase 2 (D-021). Domain `ToolBelt` (4 slots, small items only),
`ItemDefinition` ScriptableObjects, `PickupItem` world objects, `PlayerToolBelt` scene wrapper.
- Keys 1–4 select a slot; the same key again (or an empty slot) holsters.
- Taking an item with empty hands puts it in hand immediately (no extra key press).
- Hands-full rule: picking up a large `Carryable` holsters the tool; no slot switching while carrying.
- Stored items are deactivated GameObjects (no colliders); only the item in hand is visible, attached to the camera.
**Deferred:** putting small items back down, gamepad bindings, more than 4 slots, toolboxes/shelves for small items.
Placeholder item geometry may use scaled cubes (exception to D-016, which is about timber).

## D-025: Tools in hand share one contract; tape hooks on the nearest end; precision look (Accepted, 2026-11-13)
- **`IHeldTool`** (`Equip(HeldToolContext)`, `Unequip()`, `Readout` + `ReadoutChanged`). `PlayerToolBelt` equips
  the tool component of the item in hand and unequips on holster/pause. The tool's own `Update` does the work.
  Every future tool (pencil, saws, drill) follows this shape instead of a per-tool architecture (master prompt §6.3).
- **Tape measure:** hook on the board end nearest to the player when a board is first aimed at; reading = distance
  from the hook, clamped to the board, rounded to the 1 mm graduation (`TapeMeasure.Read`, `Length.RoundTo`).
  Blade drawn as a camera-facing LineRenderer along the top face. HUD readout above the crosshair.
- **Precision look** (owner-approved): hold RMB / gamepad LT → FOV 70° → 25° (200°/s) and mouse sensitivity scaled
  by FOV/normal FOV, so millimetres become aimable. Available always, not only with tools.
**Deferred:** choosing the hook end manually, measuring between arbitrary points, measuring width/thickness.

## D-026: Sticky tape hook and enlarged grab areas (Accepted, 2026-11-14)
Owner feedback after first 3a/3b try: the reading vanished as soon as the aim slipped off the board or past its
end; the pencil was hard to target.
- **Sticky hook:** once hooked, `TapeMeasureTool` keeps measuring while the aim ray passes within 0.25 m of the
  board's length axis (closest approach ray↔axis), up to 0.6 m beyond the ends (reading clamped to full length).
  Aiming at another board re-hooks; aiming far away releases.
- **Grab areas:** small items get a BoxCollider of at least 5 cm in every direction (visual unchanged), because the
  aim-assist sphere barely helps with flat objects lying on a surface (the sphere touches the surface first).
- Hand poses moved closer to the screen centre so tools stay visible in a small Game view.

## D-028: Pencil marks, cut list target and tolerance check (Accepted, 2026-11-14)
Phase 3c as agreed with the owner (LMB at the measured point draws a line; mark stored on the board; deviation
from the target reported).
- **Pencil in hand marks, the tape on the belt measures.** Real marking is two-handed (tape in one hand, pencil in
  the other). With one tool in hand, the tape is treated as laid along the board while the pencil is held: it
  must be on the belt, uses the same hook and sticky rules (`BoardAim`, shared with `TapeMeasureTool`), and its
  blade is drawn. Without a tape the pencil says so and cannot measure.
- **Stored exactly:** `PencilMark` keeps the exact aimed position (0.1 mm, from the Start end) and the reference end
  (the hooked end). The 1 mm tape reading is only what the player sees, so a mark made at reading "900" lies within
  ±0.5 mm of 900 mm: realistic and inside the ±1 mm default tolerance.
- **Marks live beside the piece**, in `BoardMarks` owned by `TimberBoard`, not in the immutable `TimberPiece`;
  Phase 4 cuts will hand them over to the resulting pieces. No eraser yet; marks reset when the scene reloads.
- **Target dimension:** a `CutList` note on the bench (E cycles 300/450/600/900/1200 mm), a stand-in for a job's
  cut list (Phase 6). Result line: `Marked at 899.6 mm  (-0.4 mm)  OK ±1 mm` or `... OUT OF TOLERANCE ±1 mm`.
  The exact deviation is shown as learning feedback (the game knows the truth; the tape shows 1 mm).
- **Visual:** a 1.5 mm dark line across the face turned towards the player (wider than a real 0.5 mm line so it is
  visible from working distance). New input action `Player/UseTool` (LMB, RT); the click that takes the pencil or
  resumes from the pause menu is ignored.
- **Cut list prompt shows the current target** ("Change target (now: 900 mm)"): the first version showed the next
  one, which the owner read as the current target (only the prompt line is shown for interactables).
- **Text uses ASCII/Latin-1 only** ("OK", "±", "×"): symbols like ✓ or → may be missing from the runtime font.
**Deferred:** eraser / removing marks, marking width or angles (square), several marks shown as a list, marks on
side faces, saving marks.

## D-029: Cutting model: parametric pieces, kerf on the waste side (Accepted, 2026-11-14)
Phase 4 plan approved by the owner ("devam et") with all recommended choices:
- **Parametric regeneration** (master prompt §6.6 asks for the trade-off): a cut produces two new domain
  `TimberPiece`s, and each gets a freshly generated box mesh, like every board today. Exact and simple for straight
  cuts; data stays the source of truth. Mesh slicing (needed for angled / free cuts) and predefined cut regions
  (inflexible) are not used now.
- **Crosscuts only**, at an existing pencil mark (`Crosscut.TryCut`); no free cuts. The skill element is the marking
  accuracy for now; saw drift may come later. Rip cuts and angled cuts are deferred.
- **Kerf on the waste side:** away from the end the mark was measured from, so the measured piece keeps exactly the
  marked length (`MeasuredPiece`); the other piece loses the kerf. Start piece + kerf + end piece = original, exactly
  (integer 0.1 mm lengths).
- **Hand saw kerf 2 mm: approximate, unverified placeholder** (like the densities, D-017).
- **Marks** are handed over: inside the kerf (incl. the cut line) they are sawn away; on the end piece positions are
  shifted to its own Start end, reference end unchanged.
- **Minimum piece length 5 mm** (`Crosscut.DefaultMinimumPieceLength`): shorter slivers are refused (`PieceTooShort`).
- **Waste = sawdust only** (`CutWaste`: kerf × cross-section, volume and mass; `MaterialWasteLog` totals). Offcuts
  remain usable pieces until the material economy (Phase 7) decides otherwise.
- The board must rest on a surface to be cut (not while carried); clamping is deferred. (Applies from 4b.)

## D-030: Hand saw interaction and splitting boards in the scene (Accepted, 2026-11-14)
Phase 4b, following D-029.
- **Hand saw** = a small item on the belt (prototype: a 500 mm saw "hangs on the belt"; a tool wall comes later).
  Data in a `SawDefinition` asset (kerf 2 mm, gameplay sawing time 0.07 s per cm² of cross-section, 1.5–8 s).
- **Targeting:** the saw snaps to the pencil line nearest to the aimed point (within 30 mm along the board). The cut
  is evaluated once per target (`Crosscut.TryCut`); a refused cut is explained before the player starts sawing.
  An orange guide line shows the kerf on the waste side next to the pencil line.
- **Sawing:** hold Use (LMB/RT); progress is kept when released and resumed on the same line, reset when the target
  changes. The saw in hand moves back and forth (`PickupItem.HandOffset`, camera space). No skill element / drift yet.
- **Splitting:** the board is copied twice with `Instantiate` (keeps all component settings: kinematic body,
  carryable, materials) and each copy gets its piece via `TimberBoard.SetPiece`; the original is destroyed. The
  pieces stay where they were, 2 mm apart. Copied mark visuals are dropped and rebuilt from the handed-over marks
  (all visuals live under one `PencilMarks` child). `PencilMark.Face` (Top/Bottom) keeps lines on the right face.
- **Waste:** `WorkshopWaste` (scene) holds the `MaterialWasteLog`; the readout shows the cut and the total sawdust.

## D-031: Unsupported objects fall and settle; cut checked against the target (Accepted, 2026-11-14)
Phase 4c (owner: "4c'ye geçebilirsin"). Fixes the known issue "removing a board from under another leaves the upper
one floating" and the new one "an offcut over the bench edge floats".
- **Settling** extends D-019 with a controlled, temporary physics state. When a resting object's support may have
  changed (after a cut: both pieces; on pick-up: objects lying on the picked one), it checks at the next physics
  step whether anything is directly below its center of mass (short ray). If not, it becomes non-kinematic and
  falls; physics decides tipping and where it lands. At rest (< 2 cm/s, < 0.1 rad/s for 0.3 s, sleeping, or after
  6 s) it is kinematic again. Objects lying on a settling object settle along. Supported objects never switch to
  physics, so placed and cut boards don't jitter or move.
- "Above" = the other object's lowest point is at least at this one's top (side-by-side boards are not affected).
- **Cut vs target:** the saw's result line checks the measured piece (the one on the reference side) against the
  cut list target with ±1 mm: `Cut: 600 mm (target 600 mm, OK ±1 mm) + 1798 mm ...`. This is the result that
  counts; the pencil's check (D-028) is the preview.
- Piece positions after a cut need no extra domain code: they follow from `KerfStart/EndFromStart` (tested).

## D-032: Assembly model: blueprint slots, connections, tolerances, explained quality (Accepted, 2026-11-14)
Phase 5 plan approved by the owner ("tamam") with all recommended choices:
- **First structure:** a 600 × 300 mm frame of spruce 95 × 45: two 600 mm rails, two 210 mm sides (300 − 2 × 45,
  butt joints), two 5 × 80 mm wood screws per corner (through 45 mm, ~35 mm into the other part). Base for the
  Phase 6 shelf. Screw size is a generic dimension, not a product.
- **Slots and anchors first** (master prompt §6.7): pieces go into predefined slots; free assembly later.
- **Tolerances:** within ±1 mm a part is accurate; up to ±5 mm it still fits but is reported as inaccurate; beyond,
  it doesn't fit. Checked per dimension (length, width, thickness).
- **Order rules:** a connection needs both parts placed; a part with any fastener in one of its connections can't be
  removed; optional slot prerequisites ("first this part") are supported but not used by the frame.
- **Fastening points** are tracked individually (`TryFasten(connection, point, fastener)`); the fastener type must
  match. Unlimited screws until the material economy (Phase 7).
- **Quality report** = separate components (parts installed, accurate parts with deviations, fasteners n/m,
  completion), no single score; it does not certify structural safety (§6.12).
- **Namespace `WoodcraftSimulator.Construction`** (not `Assembly`, which clashes with `System.Reflection.Assembly`).

## D-033: Snapping into assembly slots through a generic placement target (Accepted, 2026-11-14)
Phase 5b, following D-032.
- **`IPlacementTarget`** (Handling): anything with predefined places offers a snap pose for the carried object;
  `PlayerCarrier` asks the aimed collider's parents before free placement. The carrier knows nothing about
  assemblies; later fixed places (racks with bays, jigs) can use the same interface.
- **`AssemblyStation`** (Construction) on the assembly table root (origin = table top center): builds the domain
  `AssemblyBuild` from a `BlueprintDefinition` asset (slots with poses and nominal sizes, connections with fastening
  points for 5c), shows translucent ghosts (no colliders) of empty slots, and offers a snap when the aim point is
  within 8 cm of an empty slot's box, preferring the nearest slot the piece fits into. Not fitting → red preview with
  the reason; fits but inaccurate → green with the deviation.
- **Installed parts** are parented to the station, kinematic, and `Carryable.InstalledIn` is set: E takes them out
  again while no screw is in them; support checks skip them; the saw refuses to cut them.
- The frame lies on the table with the boards on edge (width vertical), so the 2 × 45 mm rail thickness lies in the
  frame plane and the sides are 300 − 2 × 45 = 210 mm.

## D-034: Pencil snaps to the tape graduation; mouse-wheel fine adjustment (Accepted, 2026-11-14, amends D-028)
Owner feedback: setting the exact millimetre with the mouse is hard; proposal "type the mm and the line is drawn".
Options presented: (A) type the dimension — fast but removes measuring/marking from the game; (B) realistic
assistance. Owner chose **"B now, A later as an option"**.
- **The line goes onto the graduation shown** (whole mm): a carpenter ticks at the tape's mark; precision is limited
  by the graduation, not by hand tremor. This replaces D-028's "exact aimed position" (the mark is still stored in
  0.1 mm; it simply lies on a graduation now).
- **Mouse wheel ±1 mm, Shift + wheel ±10 mm** (`Player/AdjustTool` scroll / d-pad, `Player/CoarseAdjust` Shift / LB):
  moves the pencil along the tape and holds that graduation; small mouse movements don't disturb it. Moving the aim
  more than 20 mm along the board, or onto another board / hook end, hands control back to the mouse. Domain:
  `TapeMeasure.Nudge` (stays on graduations and on the piece) and `TapeMeasure.PositionFromStart` (inverse of the
  hook distance), both tested.
- A blue preview line shows where the pencil line will go; the readout says `(wheel)` while adjusted and shows the
  wheel hint until the first line is drawn.
- What stays a skill: reading the right value, from the right end, and computing the needed dimension (e.g. 210 mm).
- **Deferred (owner): option A** as an assist setting (type the dimension) in the pause/settings menu.

## D-038: More realistic drill-driver: pilot holes, clutch (Accepted, 2026-11-15; saw part T1/T2 reverted the same day)
**Amendment (2026-11-15, owner):** T1 and T2 were reverted after the first play-test: the measurement changing while
sawing (blade drift) made the simulation "needlessly hard" ("çok saçma ... gereksiz yere çok zorlaştırıyor ... eski
haline getir"). The hand saw is back to D-030 (snaps to the nearest pencil line, hold LMB, timed); `SawingProcess`,
`Crosscut.TryCutAt` and `PlayerController.ControlsLocked` were removed. Lesson: realism must not cost playability;
ask before adding difficulty the player has to fight. The T1/T2 description below is kept as history only.

Owner approved the proposal (T1, T2, M1, M2; T3 squareness, T4 clamping, M3 screw angle, M4 free screw positions are
deferred to Phase 9). Principle: real carpentry rules in the domain, outcome from the player's input, no randomness.
- **T1 free saw placement** (replaces the snap to the pencil line of D-030): the blade is where you aim; the mouse
  wheel moves it in 0.5 mm steps (Shift: 5 mm), the mouse takes over again after 3 mm. `Crosscut.TryCutAt` centers the
  kerf on the blade. The nearest pencil line (within 30 mm) is the reference: the measured piece is the one it was
  measured for. Assist (on by default, `showCutPreview`): the HUD shows the piece length the cut would give and whether
  the blade is on the waste side or over the line.
- **T2 stroke sawing** (`SawingProcess`): hold LMB and move the mouse forward/back; looking and walking are locked
  meanwhile (`PlayerController.ControlsLocked`). Work = cross-section x 120 mm of saw travel per cm² x density/450
  (18 × 145 spruce: about 3100 mm); only movement within the 500 mm blade counts. First 10 % = starting: half
  efficiency, sideways mouse movement moves the blade along the board (0.02 mm/px), strokes faster than 900 mm/s make
  it jump (4x drift). After that the kerf guides the blade. Releasing pauses; the cut continues in its kerf on the
  same board. Gameplay values in the saw asset, not physics.
- **M1 pilot holes**: the drill-driver has a driver bit and a 3 mm drill bit, switched with the new `Player/ToolMode`
  action (Q / left stick press), 1 s to change. Rule (`FasteningRules.NeedsPilotHole`, simplified rule of thumb, not an
  engineering calculation): pre-drill wood denser than 500 kg/m³, screws thicker than 6 mm, and screws closer than
  10 x their diameter to the end of the board they go through. The end distance comes from the blueprint geometry
  (`BlueprintDefinition.ToDomain`). A screw without a needed pilot hole **splits** the board: it still holds, the
  split is drawn and reported. A drilled point locks the parts like a screw.
- **M2 clutch and screw depth** (`ScrewDrive`): wheel = clutch 1-20, then drill mode (no clutch). Seating torque =
  8 x density/450 x d/4 mm x sqrt(L/40 mm) (spruce 4 × 40: 8; 5 × 80: 14). Clutch below 60 % of it: the screw stops
  part-way; 60-100 %: it stops flush by itself; above, or drill mode: the head keeps sinking while held (max 6 mm).
  Head more than 0.5 mm out = proud, more than 1 mm deep = overdriven. A new screw driven less than 3 mm isn't set;
  a proud screw can be driven further later. The screw type comes from the joint (the drill has a box of each type).
- The quality report lists flush / standing out / too deep heads and splits separately.
